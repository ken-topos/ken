# A ctx scan reads your own report of another seat's ctx as the pane's own

The watchdog tick makes the ctx scan mandatory. I ran it as

```sh
tmux capture-pane -p -S -200 -t moot-<role> | grep -oE 'ctx [0-9]+%' | tail -1
```

and it reported **`runtime-leader: ctx 88%`** — past the ~45% the playbook calls
a monitoring miss, on the one seat that had to write the next release. I was a
step away from compacting a leader mid-flight.

**It was my own sentence.** Minutes earlier I had posted *"Verified positively:
**ctx 88% to 0%**"* about the *implementer*. The leader's pane echoed my post
while relaying it, so the scan matched **the text of my report about a
different seat** and attributed it to the pane it was captured from.

**The loop is the trap: the text most likely to contain a `ctx N%` string is a
Steward report about some seat's ctx, and it lands in the pane of whichever
seat you told.** The instrument's false positives are generated by the
instrument's own output.

**Widening the window does not fix it, and neither does narrowing.** I first
scanned `-S -6`, which missed real footers (the positional trap the compaction
playbook already warns about), then widened to `-S -200`, which bought this.
Even a `-S -15` footer window still caught the quoted text. **No window
distinguishes a footer from prose that looks like one.**

**The sound discriminator is the harness, not the window:**

- **Claude Code** panes render `ctx N%` in the footer.
- **Codex** panes (`gpt-…` on the last line) render **no ctx footer at all** —
  the playbook says to grep `context left` there, and that it is often absent
  entirely.

⇒ **Read the model line first, and only trust `ctx N%` on a Claude-Code pane.**
Any `ctx N%` appearing in a Codex pane is quoted text by construction, because
that harness never emits the string.

```sh
model=$(tmux capture-pane -p -S -3 -t moot-<role> | grep -oE 'gpt-[a-z0-9.-]+|Opus [0-9.]+|Sonnet [0-9.]+' | tail -1)
# only if $model is NOT gpt-* is a `ctx N%` match the pane's own footer
```

**The tell that you are in this failure mode:** a seat's ctx reading matches a
number you published about a *different* seat. Two seats at exactly the same
unusual percentage is not a coincidence worth explaining — it is one string,
read twice.
